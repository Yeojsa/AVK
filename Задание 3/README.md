# Пункт 1. Умножение матриц: `ijk` и `ikj`

### Внутренние циклы в ассемблере

#### 1. x86-64 (`-O2 -masm=intel`)

**`mul_ijk`**

```
.L4:
    movsd    xmm0, QWORD PTR [rdx]
    add      rax, 6144
    add      rdx, 8
    unpcklpd xmm0, xmm0
    mulpd    xmm0, XMMWORD PTR -6144[rax]
    addpd    xmm1, xmm0
    cmp      rax, rcx
    jne      .L4
    
.L7:
    movsd    xmm0, QWORD PTR [rax]
    mulsd    xmm0, QWORD PTR [rdx]
    add      rax, 6144
    add      rdx, 8
    addsd    xmm1, xmm0
    cmp      rax, rcx
    jne      .L7
```

**`mul_ikj`**

```
;   movsd    xmm2, QWORD PTR [rdi+r9*8]
;   movapd   xmm1, xmm2
;   unpcklpd xmm1, xmm1
.L25:
    movapd   xmm0, XMMWORD PTR [rcx+rax]
    mulpd    xmm0, xmm1
    addpd    xmm0, XMMWORD PTR [rdx+rax]
    movaps   XMMWORD PTR [rdx+rax], xmm0
    add      rax, 16
    cmp      r8, rax
    jne      .L25
```

#### 2. RISC-V 64-bit (`-O2 -march=rv64gc`)

**`mul_ijk`**

```
.L4:
    fld      fa4, 0(a5)
    fld      fa3, 0(a4)
    addi     a5, a5, 8
    add      a4, a4, t0
    fmadd.d  fa5, fa4, fa3, fa5
    bne      a5, a3, .L4
```

**`mul_ikj`**

```
.L4:
    fld      fa4, 0(a5)
    fld      fa3, 0(a4)
    addi     a5, a5, 8
    addi     a4, a4, 8
    fmadd.d  fa4, fa5, fa4, fa3
    fsd      fa4, -8(a4)
    bne      a5, a3, .L4
```

### Вопросы

#### 1. В x86-64 в основном SSE2-цикле `mul_ijk` элемент `a[i][k]` загружается инструкцией `movsd`, элементы `b[k][j..j+1]` считываются операндом памяти внутри `mulpd`, а `c[i][j..j+1]` загружается один раз до цикла через `movapd` и сохраняется после него через `movaps`. В `mul_ikj` элемент `a[i][k]` загружается до цикла инструкцией `movsd`, а внутри цикла `b[k][j..j+1]` читается через `movapd`, `c[i][j..j+1]` считывается операндом `addpd` и записывается обратно через `movaps`. В RISC-V все загрузки элементов `a`, `b` и `c` выполняются отдельной инструкцией `fld`, а сохранение `c` инструкцией `fsd`, вне цикла в `ijk` и внутри цикла в `ikj`.

#### 2. В `ijk` внутренний цикл идет по индексу строки `k`, поэтому адрес `b[k][j]` меняется **с шагом в целую строку**. В x86-64 это `add rax, 6144`, которая на каждой итерации сдвигает указатель по массиву `b` ровно на одну строку, тогда как указатель по `a` увеличивается на $8$ байт (`add rdx, 8`). В RISC-V указатель на `b[k][j]` в регистре `a4` на каждом шаге смещается инструкцией `add a4, a4, t0`, где в `t0` предварительно записан шаг строки $6144$ байт.

#### 3. В `ikj` внутренний цикл идет по индексу столбца `j`, из-за чего элемент `a[i][k]` остается постоянным и загружается в регистр один раз до начала цикла. Оба массива `b[k][j]` и `c[i][j]` обходятся последовательно подряд вдоль своих строк с единичным шагом по элементам. В x86-64 для обеих матриц используется общее смещение `rax`, которое на каждой итерации увеличивается на $16$ байт, позволяя за один шаг прочитать пару соседних `double` из `b`, сложить произведение с парой элементов из `c` и записать результат обратно в `c`. В RISC-V оба указателя на элементы `b[k][j]` и `c[i][j]` линейно увеличиваются на $8$ байт, а каждый элемент `c[i][j]` в теле цикла считывается (`fld`), обновляется через `fmadd.d` и сразу записывается обратно в память (`fsd`).

#### 4. В x86-64 тело основного цикла `mul_ijk` состоит из **8 инструкций**, скалярный хвостовой цикл `.L7` содержит **7 инструкций**, а тело основного цикла `mul_ikj` состоит из **7 инструкций**. В RISC-V внутренний цикл `mul_ijk` занимает **6 инструкций**, а внутренний цикл `mul_ikj` — **7 инструкций**.

#### 5. На x86-64 при сборке с `-O3 -march=native` векторные инструкции **появляются**. В генерируемом коде используются 256-битные регистры `ymm`, 512-битные `zmm`, а также инструкции `vbroadcastsd`, `vmovupd`/`vmovapd` и `vfmadd213pd`/`vfmadd231pd`. Для RISC-V векторного кода нет. При явном указании векторного расширения `-O3 -march=rv64gcv` v-код **появляется**, компилятор генерирует `vsetvli`, векторные загрузки и записи `vle64.v` / `vse64.v`, а также векторно-скалярное FMA `vfmacc.vf`.

#### 6. Оба метода выполняют одинаковое число вычислений — $n^3$ умножений и $n^3$ сложений, поэтому разница в скорости определяется не арифметикой, а работой с памятью. В `ijk` внутренний цикл обращается к `b[k][j]` с шагом в целую строку, из-за чего из каждой $64$-байтной кэш-линии используется лишь $1$–$2$ элемента `double`, а остальные данные вытесняются до повторного обращения, вызывая кэш-промахи. В `ikj` элемент `a[i][k]` удерживается в регистре на весь внутренний цикл, а строки `b[k][j]` и `c[i][j]` читаются подряд с шагом в один элемент, благодаря чему все $8$ элементов каждой кэш-линии используются на $100\%$, аппаратный предвыборщик эффективно подгружает данные заранее, а непрерывный доступ идеально подходит для SIMD-векторизации.

# Пункт 2. Штрассен: рекурсия в ассемблере

**Пролог и проверка базового случая**

```
"strassen_rec":
    push    r15
    push    r14
    push    r13
    push    r12
    push    rbp
    push    rdi
    push    rsi
    push    rbx
    sub     rsp, 200
    mov     QWORD PTR 160[rsp], r9
    mov     ebp, ecx
    mov     rdi, rdx
    mov     r12, r8
    cmp     ecx, 64
    jle     .L57
```

**Рекурсивный вызов**

```
    mov     ecx, DWORD PTR 36[rsp]
    mov     r9, QWORD PTR 104[rsp]
    mov     rdx, rdi
    mov     r8, QWORD PTR 96[rsp]
    call    "strassen_rec"
```

**Выделение, копирование и освобождение временных матриц + эпилог рекурсивной ветки**

```
    mov     rcx, rsi
    call    "malloc"
    ...
    call    "memcpy"
    ...
    mov     rcx, QWORD PTR 40[rsp]
    call    "free"
    ...
    mov     rcx, QWORD PTR 152[rsp]
    add     rsp, 200
    pop     rbx
    pop     rsi
    pop     rdi
    pop     rbp
    pop     r12
    pop     r13
    pop     r14
    pop     r15
    jmp     "free"
```

**Базовый случай `.L57` и эпилог `.L18`**

```
.L57:
    test    ecx, ecx
    jle     .L18
    ...
.L23:
    call    "memset"
    ...
.L25:
    movsd   xmm0, QWORD PTR [rdx+rax]
    mulsd   xmm0, xmm1
    addsd   xmm0, QWORD PTR [rbx+rax]
    movsd   QWORD PTR [rbx+rax], xmm0
    add     rax, 8
    cmp     rsi, rax
    jne     .L25
    ...
.L18:
    add     rsp, 200
    pop     rbx
    pop     rsi
    pop     rdi
    pop     rbp
    pop     r12
    pop     r13
    pop     r14
    pop     r15
    ret
```

### Вопросы

#### 1. В `strassen_rec` на x86-64 выполняется $7$ рекурсивных вызовов `call "strassen_rec"` по одному для каждой из семи промежуточных матриц $M_1 \dots M_7$. Перед каждым вызовом аргументы загружаются в регистры `ecx`, `rdx`, `r8` и `r9`. На RISC-V также $7$ рекурсивных вызовов представлены псевдоинструкцией `call strassen_rec` (`jal ra, strassen_rec`) с передачей аргументов в регистрах `a0`–`a3`. Вспомогательные функции `mat_add`, `mat_sub` и `base_mul` компилятор встроил напрямую в код функции.

#### 2. В прологе `strassen_rec` на x86-64 на стек сохраняются $8$ регистров (`r15`, `r14`, `r13`, `r12`, `rbp`, `rdi`, `rsi`, `rbx`), а затем инструкцией `sub rsp, 200` отрезается еще $200$ байт под локальные переменные и выгруженные указатели. Итого один кадр рекурсивного вызова занимает $264$ байта на стеке. У функции два эпилога: в базовом случае (`.L18`) выполняется `add rsp, 200`, восстановление $8$ регистров через `pop` и `ret`, а в рекурсивной ветке последнее освобождение `free(M7)` оптимизировано в хвостовой вызов `jmp "free"` сразу после восстановления стека и регистров. На RISC-V пролог аналогично сдвигает стек инструкцией `addi sp, sp, -N` и сохраняет `ra` и `s0`–`s11` через `sd`, а эпилог восстанавливает их через `ld`, возвращает `sp` и завершает функцию через `ret` (`jalr x0, 0(ra)`).

#### 3. На каждом рекурсивном шаге `strassen_rec` выполняет $17$ вызовов `call "malloc"`: сначала $8$ раз для подматриц $A_{11}\dots B_{22}$ и затем $9$ раз для временных буферов $T_1, T_2$ и матриц $M_1 \dots M_7$. В конце функции выделенная память освобождается $17$ раз: $16$ явных инструкций `call "free"` и один хвостовой переход `jmp "free"` для `M7`. Также цикл разбиения матриц `.L27` порождает по $8$ вызовов `call "memcpy"` на каждую из $m$ строк.

#### 4. Выход из рекурсии проверяется сразу после пролога сравнением с порогом `STRASSEN_THRESHOLD = 64` через инструкции `cmp ecx, 64` и `jle .L57`. Компилятор полностью встроил `base_mul` в ветку `.L57`, поэтому вместо вызова функции управление сразу попадает в код обычного умножения. Сначала цикл `.L23` обнуляет матрицу `Z` через `call "memset"`, после чего вложенные циклы `.L22`/`.L26`/`.L25` вычисляют произведение в порядке `ikj` (`movsd`, `mulsd`, `addsd`, `movsd` с шагом `add rax, 8`). По завершении умножения выполнение переходит к эпилогу `.L18` и возвращается из `strassen_rec`.

#### 5. Штрассен проигрывает на малых матрицах из-за высокой константы накладных расходов: рекурсия требует $8$ пар `push`/`pop`, $7$ вызовов `strassen_rec`, register spilling, $17$ `malloc`/`free` и множества `memcpy`, а также теряет локальность кэша при работе с $17$ временными буферами. Асимптотический выигрыш $O(n^{\log_2 7}) \approx O(n^{2.807})$ против $O(n^3)$ проявляется только при больших $n$, поскольку алгоритм меняет $8$ умножений на $7$ ценой $18$ сложений/вычитаний. Поэтому при $k \le 64$ выгоднее сразу переключиться на компактный встроенный цикл `base_mul`.

# Пункт 3. Сравнение двух ISA

#### 1. x86-64 (`-O2 -masm=intel`)

**`max2` и `max3`**

```
max2:
    cmp     edi, esi
    mov     eax, esi
    cmovge  eax, edi
    ret

max3:
    cmp     edi, esi
    cmovl   edi, esi
    cmp     edi, edx
    mov     eax, edx
    cmovge  eax, edi
    ret
```

#### 2. RISC-V (`-O2 -march=rv64gc`)

**`max2` и `max3`**

```
max2:
    bge     a0, a1, .L2
    mv      a0, a1
.L2:
    ret

max3:
    bge     a0, a1, .L4
    mv      a0, a1
.L4:
    bge     a0, a2, .L5
    mv      a0, a2
.L5:
    ret
```

### Вопросы

#### 1. На x86-64 целочисленные аргументы `a`, `b` и `c` передаются через $32$-битные регистры `edi`, `esi` и `edx`, а результат функции возвращается в регистре `eax`. Так как регистры аргументов не совпадают с регистром возврата, компилятору приходится дополнительно копировать одно из значений в `eax` инструкцией `mov`. На RISC-V аргументы `a`, `b` и `c` передаются в регистрах `a0`, `a1` и `a2`, а результат возвращается в том же регистре `a0`.

#### 2. На x86-64 при оптимизации `-O2` условных переходов (`j...`) нет — компилятор использует инструкции сравнения `cmp` и условной пересылки `cmovl` / `cmovge`. На RISC-V при `-march=rv64gc` компилятор генерирует короткие условные переходы `bge`, пропускающие инструкцию `mv`.

#### 3. На x86-64 функция `max3` занимает $6$ **инструкций** (`cmp`, `cmovl`, `cmp`, `mov`, `cmovge`, `ret`). На RISC-V функция `max3` занимает $5$ **инструкций** (`bge`, `mv`, `bge`, `mv`, `ret`), причем динамически в зависимости от входных значений выполняется от $3$ до $5$ инструкций.

# Пункт 4. Чтение цикла

#### RISC-V (`-O2 -march=rv64gc`)

**`sum`**

```
sum:
    ble     a1, zero, .L4
    slli    a1, a1, 3
    mv      a5, a0
    add     a1, a0, a1
    li      a0, 0
.L3:
    ld      a4, 0(a5)
    addi    a5, a5, 8
    add     a0, a0, a4
    bne     a5, a1, .L3
    ret
.L4:
    li      a0, 0
    ret
```

### Вопросы

#### 1. Стековый пролог отсутствует, так как `sum` является листовой функцией и использует только регистры аргументов `a0`, `a1`, `a4`, `a5`; роль подготовительной части перед циклом выполняют проверка `ble a1, zero, .L4` и вычисление конечного адреса массива (`slli`, `mv`, `add`, `li`). Само тело цикла расположено под меткой `.L3` и состоит из загрузки элемента `ld a4, 0(a5)`, сдвига указателя на $8$ байт `addi a5, a5, 8` и прибавления к сумме `add a0, a0, a4`. Проверка условия выхода вынесена в конец цикла в виде инструкции `bne a5, a1, .L3`, которая сравнивает текущий указатель `a5` с концом массива `a1` и переходит обратно на `.L3`. Возврат из функции осуществляется инструкцией `ret` сразу после завершения цикла и отдельно в ветке `.L4` (возвращает $0$, если $n \le 0$).

#### 2. Компилятор применяет оптимизацию инверсии цикла, преобразуя цикл `for` с предусловием в цикл с постусловием `do-while` с проверкой $n \le 0$ (`ble a1, zero, .L4`). Вынос проверки $n \le 0$ до цикла гарантирует выполнение хотя бы одной итерации, что позволяет оставить внутри цикла только один условный переход назад (`bne`) в конце тела цикла.

# Пункт 5. Чтение функции целиком

#### RISC-V 64-bit (`-O0 -march=rv64gc`)

**`f`**

```
f:
    addi    sp, sp, -48
    sd      s0, 40(sp)
    addi    s0, sp, 48
    sd      a0, -40(s0)
    sd      zero, -24(s0)
    sd      zero, -32(s0)
    j       .L2
.L3:
    ld      a5, -32(s0)
    mul     a5, a5, a5
    ld      a4, -24(s0)
    add     a5, a4, a5
    sd      a5, -24(s0)
    ld      a5, -32(s0)
    addi    a5, a5, 1
    sd      a5, -32(s0)
.L2:
    ld      a4, -32(s0)
    ld      a5, -40(s0)
    blt     a4, a5, .L3
    ld      a5, -24(s0)
    mv      a0, a5
    ld      s0, 40(sp)
    addi    sp, sp, 48
    jr      ra
```

### Вопросы

#### 1. В прологе без оптимизаций от стека отрезается $48$ байт инструкцией `addi sp, sp, -48`, сохраняется указатель кадра `sd s0, 40(sp)` и устанавливается новый `addi s0, sp, 48`, после чего на стек записываются аргумент `n` (`-40(s0)`) и нулевые `s` (`-24(s0)`) и `i` (`-32(s0)`). Регистр адреса возврата `ra` на стек при `-march=rv64gc` не сохраняется, так как `f` является листовой функцией и не вызывает других подпрограмм. Перед входом в цикл выполняется безусловный переход `j .L2` к проверке условия `blt a4, a5, .L3`, сравнивающей `i` и `n`. Тело цикла под меткой `.L3` загружает `i` из стека, вычисляет квадрат `mul a5, a5, a5`, прибавляет его к сумме `s` (`-24(s0)`) и увеличивает `i` на $1$ (`addi a5, a5, 1`). После выхода из цикла результат `s` переносится в регистр возврата `a0` инструкциями `ld a5, -24(s0)` и `mv a0, a5`. Эпилог восстанавливает указатель кадра `ld s0, 40(sp)`, возвращает $48$ байт стека (`addi sp, sp, 48`) и завершает функцию инструкцией `jr ra`.

#### 2. Размер кадра кратен $16$ байтам из-за обязательного требования ABI RISC-V, согласно которому указатель стека `sp` должен оставаться выровненным по $16$-байтной границе на входе в любую функцию. Такое выравнивание гарантирует корректное и быстрое размещение на стеке типов с максимальным выравниванием без штрафов за невыровненный доступ к памяти.

# Итоговые вопросы

#### 1. RISC-V следует принципу *load-store*, поэтому доступ к памяти разрешен только отдельным инструкциям `ld`/`fld` и `sd`/`fsd`, а арифметические команды работают исключительно с регистрами. Архитектура x86-64 относится к CISC и допускает комбинированные инструкции вида «регистр–память» , которые за одну команду читают операнд и выполняют операцию. За это x86-64 платит инструкциями переменной длины (от $1$ до $15$ байт), сложным и энергоемким декодером, а также необходимостью раскладывать команды на внутренние микрооперации .

#### 2. В `ijk` внутренний цикл идет по `k`, поэтому обращения к `b[k][j]` выполняются вдоль столбца с шагом в целую строку, из-за чего из каждой $64$-байтной кэш-линии используется лишь $1$–$2$ элемента `double`. В `ikj` внутренний цикл идет по `j`, поэтому элементы `b[k][j]` и `c[i][j]` читаются строго подряд с минимальным шагом. Последовательный обход задействует каждую кэш-линию на $100\%$, включает аппаратный предвыборщик и кратно снижает число кэш-промахов.

#### 3. В ассемблере `strassen_rec` рекурсия видна по $7$ вызовам `call "strassen_rec"`, перед которыми со стека загружаются аргументы и указатели. Накладные расходы на кадры проявляются в прологе и эпилоге , а также в $17$ парах вызовов `malloc`/`free` и циклах `memcpy`. На маленьких матрицах эти затраты вместе с $18$ дополнительными сложениями и вычитаниями перевешивают экономию от сокращения числа умножений с $8$ до $7$, поэтому при $k \le 64$ переходят на обычное умножение.

#### 4. Для `max2` на x86-64 при `-O2` компилятор обошелся без ветвления через `cmp` и условную пересылку `cmovge`, тогда как на базовом RISC-V из-за отсутствия условной пересылки сгенерирован короткий условный переход `bge`. На x86-64 выбор между `cmov` и условным переходом `j...` зависит от компилятора, уровня оптимизации и целевой микроархитектуры (`-mtune`/`-march`), так как у них различаются модели стоимости инструкций. Ветвление бывает быстрее на предсказуемых данных за счет отсутствия зависимости по данным, а `cmov` выигрывает на случайных данных, исключая штраф за промах предсказателя переходов.

#### 5. Архитектура x86-64 сохраняет строгую обратную совместимость, поэтому процессор $2025$ года полностью поддерживает базовый набор инструкций $2005$ года. Флаг `-march=native`, разрешает компилятору использовать новейшие расширения конкретного процессора, на котором собирается программа. При запуске такого бинарного файла на другой машине без этих инструкций выполнение завершится ошибкой `Illegal instruction`.
